**4. 왜 그렇게 설계했는지**

예약 신청은 Firebase 접근을 ViewModel에서 직접 하지 않도록 `ReservationRepository`로 분리했습니다. AGENTS.md의 Repository Pattern, MVVM 규칙을 지키기 위한 구조입니다.

Host 예약 화면은 `reservationLinkId`만 받아서 `UserRepository`로 Host를 찾고, `TimeSlotRepository`로 AVAILABLE 슬롯을 조회합니다. 공유 링크 진입 구조와 Firestore 스키마를 그대로 맞추기 위해서입니다.

예약 생성 시에는 `reservations` 문서만 만들고 `time_slots` 상태는 변경하지 않았습니다. 문서 규칙상 신청 단계에서는 `PENDING` 예약만 생성하고, 슬롯을 `RESERVED`로 바꾸는 것은 승인 STEP에서 처리해야 하기 때문입니다.

중복 예약 방지는 신청 시점에 `slotIds array-contains` + `status in [PENDING, APPROVED]`로 검사했습니다. MVP 정책상 같은 슬롯에 여러 PENDING 예약을 허용하지 않기 때문입니다.

UI는 날짜 드롭다운 + 시간 그리드로 바꿨습니다. 같은 날짜가 반복되는 리스트보다 날짜를 한 번 선택하고 시간만 고르는 방식이 훨씬 스캔하기 쉽고, 모바일 화면 낭비도 적습니다.

**5. 반드시 이해해야 하는 코드 5곳**

1. `FirestoreReservationRepository.requestReservation(...)`
    - 예약 신청의 핵심 로직입니다.
    - 슬롯 존재 여부, Host 일치, AVAILABLE 상태, 과거 시간, 연속 슬롯, 중복 예약을 검사한 뒤 `reservations` 문서를 생성합니다.

2. `HostReservationViewModel.selectSlot(...)`
    - Guest가 시간 슬롯을 선택할 때 연속 슬롯 범위를 자동 선택하는 로직입니다.
    - 첫 슬롯과 두 번째 클릭 슬롯 사이가 연속이면 범위 전체를 선택합니다.

3. `HostReservationViewModel.loadHostReservationPage()`
    - `reservationLinkId`로 Host를 찾고, 해당 Host의 예약 가능한 슬롯을 불러옵니다.
    - Host 예약 링크 화면 진입의 시작점입니다.

4. `HostReservationScreen.DateSelector(...)` + 날짜 필터링 부분
    - 슬롯 날짜 목록을 드롭다운으로 보여주고, 선택한 날짜의 슬롯만 화면에 출력합니다.
    - 날짜 중복 표시 문제를 해결한 부분입니다.

5. `MainActivity`의 `HostReservation("host/{reservationLinkId}")` route
    - Host 예약 화면으로 진입하는 Navigation 연결입니다.
    - 홈의 “내 예약 링크 열기” 버튼도 이 route로 이동합니다.
