**3. 새로 사용한 기술**
완전히 새로운 외부 라이브러리는 추가하지 않았습니다.

이번에 새로 쓴 Android/Compose API는:
- Compose `OutlinedTextField`: reservationLinkId 테스트 입력
- Compose `LocalClipboardManager`: 링크 ID 클립보드 복사
- Compose `verticalScroll`: Home 화면 컨텐츠 증가에 따른 스크롤 대응
- Navigation Compose route 추가: `reservations/{mode}`, `reservation/{reservationId}`

Firebase는 기존 Firestore 사용 방식 그대로입니다.

**4. 왜 그렇게 설계했는지**
Repository Pattern을 유지했습니다. Firestore 조회는 `FirestoreReservationRepository`와 `UserRepository`에만 두고, ViewModel은 Repository 함수만 호출합니다. 그래서 AGENTS 규칙의 “ViewModel에서 Firebase 직접 호출 금지”를 지켰습니다.

예약 목록은 Host/Guest 목록이 거의 같은 화면 구조라 `ReservationListMode.RECEIVED`, `ReservationListMode.MINE`으로 하나의 ViewModel/Screen을 재사용했습니다. 화면만 중복해서 만들면 STEP 6 범위에 비해 코드가 불필요하게 늘어납니다.

예약 상세는 목록과 분리했습니다. 목록은 여러 예약을 가져오는 화면이고, 상세는 단일 예약 권한 확인과 표시가 핵심이라 ViewModel을 따로 두는 게 명확합니다.

테스트용 링크 입력은 STEP 9의 App Links를 구현하지 않고, 기존 `host/{reservationLinkId}` 내부 route로만 연결했습니다. 즉, 실제 공유 링크/Hosting/App Links는 건드리지 않았고, 현재 STEP 검증에 필요한 최소 진입 경로만 추가했습니다.
